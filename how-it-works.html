How this radar is built

A personal news radar for the AI and startup ecosystem: 36 RSS feeds, a deterministic scoring pass, and exactly one call to a local language model per hour. This page explains every stage, why each decision was made, and what went wrong on the way.

The short version

Radar has one job: tell one developer what actually happened in AI today, and let them dig further if they want. It does that with two views — a curated Brief and a browse-everything Explore — backed by a local SQLite database and an hourly scan.

The one decision everything else follows from

Collection and scoring are deterministic code. The language model is used for exactly one step — turning a pre-ranked list of headlines into a ranked brief. The model never fetches a page, never chooses what to look at, and can only ever reference items it was handed, by number.

The whole system, in numbers, from the last scan at the time of writing:

561
headlines seen across 36 feeds (36 ok, 0 failed, 6 s timeout budget per feed)
130
candidates after dedupe, topic scoring and a hard cap — the only thing the model sees
14
items in the finished brief: 1 lead + 13 entries across 6 sections

The funnel is the point. Roughly 97.5% of collected headlines never reach the brief, and the model spends its judgement on a list that has already been narrowed by code.

  • One scan = fetch 36 feeds → clean and score → store → one model call → resolve → store the brief. About 50 seconds, most of it waiting on the model.
  • It refreshes itself every 60 minutes, plus a button in the UI and an HTTP endpoint.
  • Nothing is trusted from the model except its judgement about which numbered item matters. Every displayed story is a real database row.
  • No build step. The frontend is one HTML file, one CSS file, one JS module. Two runtime dependencies in total.

The approach

The obvious way to build an AI news digest is to hand an agent a set of sources and let it browse, read, and write. That is also the fragile way. A browsing agent is slow, its cost scales with how much it reads, it can silently skip a source, and the same prompt can produce a different digest each run because the inputs were never fixed.

Radar inverts that. It splits the job into the part that should never be left to judgement and the part that genuinely needs it:

The split, and why each side is where it is
Step Who does it Why
Fetch 36 feeds Deterministic code Fetching is mechanical. A model here is slower, costlier, and non-reproducible.
Clean text, classify topics, score, dedupe Deterministic code Rules are auditable and instant. You can read exactly why an item scored 74.
Store everything SQLite Nothing is lost if curation fails. Explore works regardless.
Choose the lead, write the notes, group into sections A local model This is real judgement: what matters today, and why, for one reader.
Map the brief back to real records Deterministic code Makes the model's output safe to render even when it is wrong.
design principle

The model is treated as an unreliable narrator with good taste. Its opinions are the product; its facts are always re-sourced from the database.

What "one model call" actually means

Radar opens a single OpenCode session, sends one prompt containing the numbered candidate list, and reads back one JSON object. There is no tool calling, no multi-turn loop, no agent memory. That constraint is what makes the run cost predictable and the failure mode obvious: either valid JSON comes back, or the scan is marked failed and the previous brief stays on screen.

The pipeline

Six stages, executed in order, once per scan. Each stage names the file that owns it — the whole backend is eleven small modules, and this is the map.

Stage 1 — Collect

server/collect.js fetches every configured feed, parses it, and turns each entry into a normalised item. It handles RSS 2.0, RSS 1.0/RDF, and Atom in one parser by being generous about where the entry list lives and where the link, date, author and body hide: 

// collect.js — one parser, three feed dialects
function extractEntries(doc) {
  const root = doc?.rss?.channel ?? doc?.feed ?? doc?.RDF ?? doc?.rdf ?? doc
  const channel = root?.channel ?? root
  const items = channel?.item ?? root?.item ?? root?.entry ?? channel?.entry
  return asArray(items)
}

Fetching runs through a small bounded pool — six feeds in flight, each with its own 15-second abort signal — so one slow host cannot stall the scan: 

// collect.js — bounded concurrency, no external dependency
export async function mapPool(values, limit, worker) {
  const results = new Array(values.length)
  let cursor = 0
  const runners = Array.from({ length: Math.min(limit, values.length) }, async () => {
    while (true) {
      const index = cursor++
      if (index >= values.length) return
      results[index] = await worker(values[index], index)
    }
  })
  await Promise.all(runners)
  return results
}

Every source is recorded in a source_health table on each scan — when it last succeeded, what it returned, how long it took, and the last error if it failed. That table is what feeds the "36 ok, 0 failed" line in the UI, and it is how a quietly broken feed gets noticed instead of silently dropping out of the digest.

item identity

Each item gets an id from fingerprint(sourceId, url || title) — a short SHA-1. Because it is content-derived rather than random, re-seeing the same story on the next scan updates the existing row instead of inserting a duplicate.

Stage 2 — Clean and score

Raw feed text is dirty. Hacker News descriptions are literally Article URL: … Comments URL: … Points: 862 # Comments: 431. Reddit entries lead with a preview image URL. This stage strips all of that, classifies each item into a topic, gives it a 0–100 signal score, and collapses duplicates.

Cleaning

// text.js — the patterns that actually occur in these feeds
text = text.replace(/\b(?:article|story|link|video|comments?)\s*url:\s*\S+/gi, " ")
text = text.replace(/#?\s*comments?:\s*\d+/gi, " ")
text = text.replace(/\bpoints:\s*\d+/gi, " ")
text = text.replace(/https?:\/\/\S+/gi, " ")
// …then: if what is left merely repeats the headline, return "" so the UI omits it.

The last line is the subtle one. After removing URLs and labels, a lot of entries reduce to the headline again — so the cleaner compares the residue against the title and returns an empty string when there is nothing new to say. The UI then simply drops the summary line rather than printing the title twice.

Topic classification

Six topics drive both the filters and the colours. Each is a keyword list; an item is scored by how many of a topic's keywords it matches (multi-word keywords count double, since they are more specific), and the best match becomes the primary topic:

Scoring

Scoring starts from a base of 28 and moves it by explicit, readable rules — recency tiers, the source's weight, and keyword signals that experience says predict a story worth reading: 

// rank.js — signal rules (excerpt)
[/[$€£]\s?\d[\d.,]*\s?(m|b|bn|billion|million)\b/i, 18],   // a concrete money figure
[/\b(series [a-e]|seed round|valuation|acquir|merger|ipo)\b/i, 14],
[/\b(raises|raised|funding|invest)\b/i, 12],
[/\b(launch|launches|releases?|shipped|announce|unveil)\b/i, 9],
[/\b(open[- ]?source|open[- ]?weights?|apache 2|mit license)\b/i, 10],
[/\b(api|sdk|pricing|rate limit|endpoint|mcp|integration)\b/i, 8],
[/\b(benchmark|sota|outperform|beats|score[sd]?)\b/i, 8],

Noise rules subtract for opinion pieces, podcasts, top-N roundups, tutorials and sponsored posts. The result is clamped to 0–100 and stored. That number is what makes the bars in the 24-hour strip different heights.

Deduplication

The same story syndicated across four outlets should be one line in the brief, not four. dedupe() sorts by score, then drops any item whose title is similar enough (a token-overlap ratio above 0.62) to an already-kept one. The losers are not discarded — they are attached to the survivor as alsoOn, which is where the "also covered by …" line under a story comes from.

The surviving list is sorted best-first, capped at collection.maxCandidates (130), and then re-sorted newest-first before being written into the prompt — because the curator reads top-down and should meet today's news first.

Stage 3 — Store

Everything lands in one SQLite file via Node's built-in node:sqlite — no native module, no ORM, no separate service. Four tables carry the whole system:

Schema at a glance — data/radar.db
TableHoldsNotable columns
items Every headline ever collected primary_topic, score, read_at, saved, brief_id
briefs One row per curation attempt payload (the resolved brief as JSON), status, candidate_count, duration_ms
scans One row per scan run feeds_ok, feeds_failed, items_seen, curate_ms, step
source_health Per-feed status last_ok, last_count, last_ms, last_error

The insert is an UPSERT keyed on the content fingerprint, so re-seeing a story refreshes its title, summary and score without duplicating it. Writes run in WAL mode, which is what lets the HTTP server keep reading while a scan is writing.

self-healing rows

After inserting, every scan re-enriches the whole collection window and writes the results back with updateItemMeta(). That means changing a keyword, a mute rule, or the summary cleaner repairs existing rows on the next scan instead of leaving the database half-old. npm run reclassify does the same thing across the entire store on demand.

A scan writes its own funnel into the scans table as it goes, updating the step column at each stage — reading sources, curating, done. That is both the audit trail and the source of the live progress text in the UI.

Stage 4 — Curate

This is the only stage with a model in it. server/curate.js opens one OpenCode session, sends one prompt, and reads back one JSON object.

The prompt is a list, not a task

The entire prompt payload is a header plus one line per candidate, rendered as a stable, sparse-numbered list. The model is never shown URLs to fetch or files to read; it is shown text, and asked to reply with text: 

Scan window: 2026-10-16T07:12:00.000Z to 2026-10-16T08:00:00.000Z
Candidates: 130

[1] id=9f2c… | TechCrunch AI | 2h ago | Anthropic's Q3 revenue hits $16.8B… | …
[2] id=41ba… | Hugging Face  | 3h ago | Muse Spark Open weights are live… | …
… 128 more lines …

The reply is a strict shape

The curator's instructions live in a single file — .opencode/agents/radar.md — which is the source of truth used by both execution modes. It asks for raw JSON only, with a headline, one lead, sections keyed by topic, and a short watchlist: 

{
  "headline": "one line, max 100 characters",
  "lead": {
    "itemId": 3,
    "why": "2-3 sentences: what happened and why it matters",
    "context": "1 sentence of background or what to watch next"
  },
  "sections": [
    { "id": "models", "entries": [ { "itemId": 7, "note": "one sentence", "alsoCoveredBy": [9] } ] }
  ],
  "watchlist": ["max 3 short lines"]
}

The rules in that file are opinionated and worth reading in full. The load-bearing ones: keep at most 3 entries per section and 14 total, omit an empty section rather than padding it, never reuse an item across sections, prefer the primary source when collapsing a story, and drop opinion pieces, listicles, roundups, podcasts and sponsored posts outright.

Parsing a reply that may be wrapped in prose

Models add commentary and markdown fences. Rather than trusting the reply to be clean, server/json.js scans for the first balanced {…} object, tracking string state and escapes so braces inside notes do not confuse it: 

// json.js — balanced-brace scan, string- and escape-aware
if (char === '"') inString = true
else if (!inString && char === '{') depth += 1
else if (!inString && char === '}') {
  depth -= 1
  if (depth === 0) return JSON.parse(source.slice(start, i + 1))
}

The rule that cost the most time

OpenCode serves some models for free from the opencode provider — but only when the request looks like a stock session. Attach a custom system prompt, a permission override, or a named agent, and the gateway treats it as third-party traffic and refuses it outright:

the error, verbatim

"OpenCode's free tier can only be used from within OpenCode…"

So the curator runs in one of two modes, chosen from the provider id. Free opencode models run plain: no agent, no permissions, and the curator instructions prepended into the prompt itself. Any provider you configured yourself (like nvidia) has no such restriction, so there the session is locked down to the tool-free radar agent with a deny-all permission set. 

// curate.js — one rule decides how the session is built
export function curatorMode(model) {
  if (model?.mode === "plain" || model?.mode === "locked") return model.mode
  return model?.providerID === "opencode" ? "plain" : "locked"
}

Plain mode

providerIDs: opencode
  • No agent override.
  • No permission override.
  • Instructions prepended inline.
  • Required for the free tier.

Locked mode

every other provider
  • Uses the radar agent.
  • Deny-all permissions.
  • No tool could be reached anyway.
  • Keeps the prompt clean.

The instructions themselves never fork — both modes use the same markdown body, loaded from .opencode/agents/radar.md. Only the delivery changes: as a system prompt in locked mode, as an inline prefix in plain mode.

Stage 5 — Resolve

The curator answers with item numbers. resolveBrief() is the code that turns those numbers back into real database rows — and it is the reason a wrong model cannot corrupt what you read.

Two guards make this safe. First, a number is consumed at most once, so an item cannot appear in two sections: 

// curate.js — a number is either valid and unused, or it is dropped
const take = (rawId) => {
  const n = Number.parseInt(rawId, 10)
  const item = byNumber.get(n)
  if (!item || used.has(n)) return null
  used.add(n)
  return item
}

Second, the "also covered by" list is rebuilt from two sources and de-duplicated by source name: the cross-references the model listed, plus the syndicated outlets the dedupe pass already attached to the item. That merge is why a story can show three other outlets even when the model only named one — and why the same outlet never appears twice.

Section ids are validated against a whitelist and re-sorted into a fixed order, notes are truncated, and the watchlist is capped at three lines. Anything malformed is dropped silently. The brief that comes out is always internally consistent, even when the model's judgement is questionable.

Worst case, stated plainly

If the model mismatches a note to the wrong story, you get a good story with a note meant for another one. You never get a story that does not exist, a broken link, or a duplicated entry — because every rendered story is a row that was collected and stored by code.

Stage 6 — Serve and render

server/index.js is a plain node:http server: static files from public/, a small JSON API, and a server-sent-events stream so the browser can watch a scan progress without polling.

The hourly loop

A single self-rescheduling timer computes how long until the next scan is due (based on the last scan's start time plus refreshMinutes), waits, runs a scan if one is not already in flight, and reschedules. A separate interval prunes history every twelve hours — items older than 60 days, briefs older than 90. A scan already running is never started twice; the guard is a single in-flight promise.

The two views

Brief leads with the day's lead story on a chartreuse block — the one place in the app where the highlighter appears, because it marks the curator's single biggest judgement — followed by the themed sections and a short watchlist. Explore is everything stored: filter by topic, source, text, unread or saved, with day separators and a tooltip on every bar of the strip.

Design decisions, briefly

  • Cool green-grey paper and near-black green ink — deliberately not the cream-and-terracotta default.
  • One accent, chartreuse, used only for judgement: the lead block and the live-status dot.
  • Topic colours are data, not decoration: the same six hues appear in the strip, in section swatches, and in Explore chips.
  • Archivo with its variable width axis for display and UI, Newsreader for prose.
  • No border-radius, no cards, no all-caps eyebrow labels — the page should read like a signal desk, not a dashboard.
  • One orchestrated motion: the strip bars rise with a 13 ms-per-slot stagger, and nothing else animates for its own sake.
  • Dark mode follows prefers-color-scheme; the strip and the chips keep their meanings in both.

The sources

Thirty-six feeds, all verified working, chosen so that each one answers a question the others cannot. Each source carries a weight that is added to its items' scores, because a lab's own announcement is worth more than a search-result echo.

on the Anthropic and Meta gap

Neither publishes a feed of its own, so their news arrives through press, community and the Google News queries rather than a first-party source. That is a real asymmetry in the source list, not an oversight — it is also why the Anthropic query exists as a dedicated feed.

Two per-source levers exist beyond weight: limit caps how many entries are taken from a feed (arXiv takes 12 and 10; the release feeds take 6–8), and the global windowHours of 48 decides how far back an item may be to stay eligible.

How it was built

The order of work mattered, and several early assumptions were wrong. This is the honest sequence.

First: prove the ground, not the feature

Before writing the app, the environment was probed: Node version, whether node:sqlite actually works, whether the npm registry is reachable, whether the OpenCode service can be reached from a plain Node process at all. That last one is where the first real discovery was.

Dead end: the embedded SDK

The obvious path was the OpenCode SDK as a library. It does not work under a plain Node process — it fails importing drizzle-orm/column.js, because the package ships only the .cjs build of that file. Rather than fight it, the client was pointed at the already-running OpenCode background service instead: discover it with Service.ensure(), then create sessions over HTTP. That removed the broken dependency entirely and turned out to be the more honest architecture anyway — the app talks to the service exactly as any other client would.

Then: build the boring 80% first

Collection, cleaning, scoring, and storage were written and verified before any model was involved. Feeds were probed individually with a small verify-sources script until all 36 returned usable entries — that step caught feeds that parse but yield zero items, which is a different failure from an HTTP error and would otherwise be silent.

Then a full scan was run end to end with curation disabled, purely to check the numbers: how many items are actually seen per scan, how much dedupe collapses, how many candidates survive the cap. Only once that funnel looked right was the model wired in.

The classification bug

The first full scan produced a brief where every single item was filed under Industry. The cause was ordering: items were being written to the database before topic enrichment ran, so the stored row kept the schema default. The fix was to enrich before the insert, and — more importantly — to add a backfill that re-enriches the whole window on every scan, so a row can never be left stale by a later change to the rules.

Choosing the curator by A/B, not by vibes

Two models were run against the same real 130-candidate set and the resulting briefs read side by side. The free DeepSeek model won clearly: better coverage, specific numbers preserved, and the correct story chosen as the lead. The other candidate worked but attached a note to the wrong item — exactly the failure mode the resolve stage exists to contain. That comparison script was kept as npm run compare-models.

Finding the free-tier rule

The single most time-consuming discovery: free opencode models refuse to answer as soon as the session carries a custom system prompt or a permissions override. This was found by bisecting the session parameters until the call succeeded, and it directly shaped the plain/locked split described above. It is also why the curator instructions live in one markdown file and get delivered two different ways, rather than being maintained twice.

Last: the frontend, and fixing what it revealed

The UI came last, and building it surfaced data problems that the API alone had hidden: duplicated "also covered by" outlets, summaries that were just Hacker News footers, and summaries that repeated the headline. Each was fixed at the layer that owned it — mostly in the cleaner and the resolver — with the UI holding only a thin defensive check, not the fix itself.

why the model was never asked to fetch anything

Every problem above is a problem about inputs. By fixing the inputs with deterministic code, the model's only remaining job is judgement — and judgement is the thing it is actually good at, and the only thing whose failure the resolve stage can absorb.

What surprised me

The non-obvious behaviours, in rough order of how much time each one cost.

  • free tier A custom system prompt is what breaks free models

    The restriction is not about how many requests you make or which model you pick. It is about whether the session looks like a stock one. A permission override alone is enough to trip it — which is counter-intuitive, since the whole point of a deny-all permission set is to be more restrictive, not less.

  • ordering Enrich after insert silently defaults everything

    The database defaults primary_topic to industry. If classification runs after the write, you get a plausible-looking database where everything is "Industry" and no error anywhere. This is the class of bug that only a full end-to-end scan reveals.

  • feed data A broken feed is not always an error

    A feed can return HTTP 200 and parse cleanly while yielding nothing usable. Feeding it three entries and checking they are non-empty catches both failures at once.

  • text The noisiest source field is the one you least expect

    Hacker News descriptions are raw link-plus-comment metadata. They looked like real summaries until they were rendered in a list next to each other — which is an argument for building the UI early enough to see what the data actually looks like.

  • model output A wrong answer and an unusable answer need different handling

    If the model returns prose instead of JSON, the whole brief fails and the previous one stays up with an error state. If it returns valid JSON with bad judgement, you get a slightly worse brief. Treating those as the same failure would either be too brittle or too forgiving.

  • packaging It ran fine and still would not have installed

    The app worked for days while package.json declared no dependencies at all, because node_modules already existed on disk. A fresh clone would have installed nothing. It was caught by trying a clean install in a scratch directory — worth doing before calling anything "done".

What's next

The honest open edges, roughly in the order I would tackle them.

  • First-party coverage for the labs without feeds. The Google News queries are a workaround; a proper source for Anthropic and Meta announcements would close the one real gap in the source list.
  • Evaluation of the curator, not just A/B. Right now model quality is judged by reading two briefs side by side. A small fixed candidate set with a known good answer would make regressions visible automatically.
  • Cross-scan story continuity. The brief knows what happened today; it does not know that a story is the third development in a thread it has covered all week.
  • Retention of the model's reasoning. Failed curations store the raw reply, but successful ones discard it — keeping it would make bad judgement diagnosable after the fact.
  • A second opinion on the lead. The single most consequential choice in the whole system is made by one model call with no check on it.
